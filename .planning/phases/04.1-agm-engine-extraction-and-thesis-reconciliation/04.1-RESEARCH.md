# Phase 4.1 Research

## Existing Architecture

`gen_eval` calls callback functions exported by `maxhml_eval` while assembling a generated monitor module. `maxhml_eval` currently mixes three responsibilities:

1. traversal of the parsed maxHML formula and generation of modular monitor-state functions;
2. generation of property-specific event-reduction functions and transition-table AST; and
3. generation of reusable AGM algorithms directly into every monitor module.

The generated AGM transition representation is:

```erlang
{SourceState, DestinationState, EventDescriptor, EventPredicate}
```

The Phase 4 characterization suite exercises both generated helper functions and actual generated monitor states for unique, ambiguous, impossible, literal-multiplicity, and symbolic-domain cases.

## Target Architecture

- `agm_engine.erl`: reusable, pure functions over transition data and reduction callbacks.
- `maxhml_agm_codegen.erl`: Erlang syntax-tree construction for transition data, monitor reductions, runtime adapters, ETS/message boundaries, and generated calls into `agm_engine`.
- `maxhml_eval.erl`: maxHML traversal plus callback delegation required by `gen_eval`.

Generated monitors keep property-specific transition predicates and reduction continuations. Generic inference and consequence aggregation execute in `agm_engine`.

## Verification Strategy

- Add direct EUnit tests for pure engine outcomes and side-effect independence.
- Preserve the eight Phase 4 generated-monitor scenarios.
- Run the full default suite after each extraction boundary.
- Inspect generated source to prove remote `agm_engine` calls and the absence of duplicated generic AGM algorithms.
- Build the complete thesis and record chapter-level evidence.
